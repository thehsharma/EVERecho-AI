19  The next five actions

In order. The first two are not engineering work, which is why they are first.

Action Detail
1 Send the consent copy to counsel All of it: the five modes, the nine activities, the teach-back wording, the succession screen, the deletion warning and the terms. Four jurisdictions. Nothing else on this list matters if the consent is not sound, and the wording is currently a draft written by engineers.
2 Name the accountable person One human being who reads the audit trail weekly and who is escalated to when a consent or safety incident occurs. The runbook currently escalates into a vacuum. This is a decision, not a task.
3 Build the production authentication path OIDC or passkeys, plus MFA enrolment. Today AUTH_DRIVER=local is refused when NODE_ENV=production, which means the product cannot be deployed at all. Add a password reset flow in the same piece of work — its absence is currently a support burden waiting to happen.
4 Run the stack under Docker Compose, then wire the real providers In this order: Compose up and watch the migrate step; then S3 or MinIO with a real upload, presigned download and deletion; then Redis, verifying that revocation clears keys across two API instances; then pgvector, verifying that its results match the portable path. Each one is complete code that has never run.
5 Commission the independent security review, and rehearse a restore and a deletion The review should focus on the consent engine and the RLS boundary. The rehearsals should be performed by someone who did not build the system, end to end, with the deletion verified against the database afterwards rather than against the receipt.
What is deliberately not on this list

Features. There is no shortage of things this product could do — a contributor review queue, notification digests, a rendered ERD, richer biography editing. None of them should be built before items 1–5, because every one of them adds surface area to a system whose foundations have not yet been reviewed by anyone outside the team that wrote them.

Where to start reading the code

Three files carry most of the product's meaning. Read them in this order.

  1. packages/consent/src/authorize.ts — the single decision point. Pure, no I/O, and the order of its checks is deliberate: prohibited action, then unauthenticated, then the admin path, then archive lifecycle, then membership, then the buyer special case, then the role table, then consent. Every reordering the tests rejected is a bug that would have leaked something.
  2. apps/api/src/lib/access.ts — how a request becomes an archive-scoped transaction, and why the deny audit is written on a different connection.
  3. apps/api/src/modules/qa.ts — how a question becomes a cited answer or an abstention, with the safety checks ahead of retrieval rather than behind it.
The last word

This document contains no projected figures, no mockups and no claims that were not produced by running the code. Where something was built but never executed, it says so; where something is missing, it is named. That discipline is not incidental to the product — a system whose entire value rests on refusing to state what it cannot support should be described the same way.
