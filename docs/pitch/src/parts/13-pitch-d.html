How an answer is actually produced

question │ ├─ 1. prohibited-request check ──────── refuses "pretend to be her" etc. ─▶ refusal ├─ 2. prompt-injection check ────────── isolates instructions in content ─▶ refusal │ ├─ 3. authorize(actor, 'qa.ask', …) ─── ALLOW + obligations, or DENY │ obligations: maxSensitivity, excludedSourceIds, restrictedTopics │ ├─ 4. retrieval ── obligations become part of the SQL WHERE clause, │ not a filter applied afterwards │ lexical : OR-based to_tsquery over generated tsvector columns │ semantic : cosine distance over real[] embeddings (PL/pgSQL), │ or pgvector + HNSW where the extension is present │ ranking : 0.6 lexical + 0.4 semantic, deterministic tie-break │ ├─ 5. composition ── extractive: quotes and stitches retrieved passages. │ Structurally cannot originate a claim. │ ├─ 6. verifyClaim() ── content-word coverage of each material claim │ against its cited passage. Failures are dropped. │ ├─ 7. assertThirdPerson() ── first-person voice as the subject → discard │ └─ 8. answer + citations, or abstention
The abstention sentence, verbatim

“I don't have enough evidence in this archive to answer that reliably.”

It is a fixed string. It is not softened, not padded with a suggestion, and not followed by a guess. In the evaluation suite, 100% of no-evidence and sensitive-topic cases produce it.

Why the filter goes in the WHERE clause

The tempting implementation is to retrieve broadly and then remove results the viewer may not see. That is wrong in a way that is invisible until it matters: the ranking, the summary, and the model's context have all already been shaped by material the viewer is not permitted to know exists. A count, a date range, even a refusal phrased slightly differently can leak the presence of an embargoed memory. Here the obligations returned by authorize() are compiled into the query itself, so excluded material is never retrieved, never ranked and never seen by the composer. Decision D‑010.

Why the composer is extractive

The local composition adapter can quote retrieved passages and join them; it has no mechanism for producing a sentence that is not derived from retrieved text. This is a strictly weaker system than a hosted model, and the answers read more plainly as a result. It is also a system in which fabrication is not something to be measured and reduced — it is unavailable. The hosted Anthropic adapter is implemented with forced strict tool use and runs behind the same verification and third-person gates, so the safety property survives the upgrade; but it has never been executed in this build, and Part III says so.

And what is not true

Eight integrations are complete and type-checked but were never executed, because nothing was reachable from the build environment: Docker Compose, S3/MinIO storage, Redis, pgvector, the hosted Anthropic composer, hosted speech-to-text and OCR, SMTP email, and Stripe. Stripe's verifyWebhook currently returns null — it fails closed, which is the safe direction, but it must be wired before billing is enabled.

The honest verdict

Not ready for a real family's memories. Ready to be run, reviewed and piloted internally with synthetic data.

What is built is genuinely built — the consent engine, provenance, isolation and deletion are the parts most likely to be faked in a project like this, and they are the parts with the most tests behind them. What is missing is largely operational, plus four things that need a person rather than an engineer: legal review, a security review, an accessibility review with disabled users, and a decision about who is accountable when something goes wrong.
