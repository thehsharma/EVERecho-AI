12  Command reference

Every command is run from the repository root. There is no build step: packages are consumed as TypeScript source and executed through tsx.

Setting up and running

CommandWhat it does
pnpm setupInstall, migrate and seed in one step.
pnpm db:migrateApplies the eight numbered SQL migrations. Each is checksummed; a migration whose contents changed after being applied is refused rather than re-run.
pnpm db:seedBuilds the synthetic demonstration archive by running the real ingestion pipeline.
pnpm db:resetDestructive. Drops and recreates the schema. Never point this at anything you care about.
pnpm dev:apiThe Fastify API on :4000.
pnpm dev:workerThe background job runner.
pnpm dev:webThe Next.js application on :3000.
pnpm devAll three in parallel, in one terminal.

Checking that it is sound

CommandWhat it does
pnpm verifyThe one that matters. Runs format check, lint, typecheck, all unit and integration tests, and the AI evaluation suite, in that order. This is what CI runs.
pnpm typechecktsc --noEmit across the entire workspace graph, web application included.
pnpm lintESLint 9 flat config.
pnpm test145 unit tests and 48 integration tests. The integration project runs against a real PostgreSQL — there are no database mocks anywhere in the suite.
pnpm test:unitUnit project only; needs no database.
pnpm test:integrationIntegration project only; needs DATABASE_URL.
pnpm test:e2e54 Playwright tests including the axe-core accessibility scan. Needs the stack running.
pnpm evalThe 32-case AI evaluation suite. Exits non-zero if any release-blocking target is missed, which is what makes the targets blocking rather than advisory.
pnpm openapiRegenerates docs/openapi.json from the same Zod schemas that validate requests at runtime, so the document cannot drift from the implementation.
Do not weaken a failing test to produce green CI

Four real bugs in the consent engine were found by tests written before the engine was finished — a reason-code ordering error, a granularity collapse in the mode-to-activity mapping, two roles missing their export actions, and a code path that skipped the recipient-grant lookup entirely. Each looked, at first, like an over-strict test.

Verifying the isolation yourself

Row-level security is the claim most worth checking by hand. Two queries do it:

-- With no archive scope set, every content table returns nothing.
SELECT count(*) FROM memory;                       -- 0

-- Inside a scope, the archive's own rows are visible.
BEGIN;
SELECT set_config('everecho.archive_id', '<archive-uuid>', true);
SELECT count(*) FROM memory;                       -- the real count
-- and a write aimed at a different archive is rejected by the policy
INSERT INTO memory (archive_id, ...) VALUES ('<other-uuid>', ...);  -- ERROR
COMMIT;

Both were run directly against the database in the session that produced this repository, and both behaved as described. FORCE ROW LEVEL SECURITY means the table owner is subject to the policy too, so this holds even for a connection with database-owner privileges.

13  When something goes wrong

SymptomWhat it means, and what to do
/readyz returns degraded Usually expected. With CACHE_DRIVER=memory and no pgvector extension, readiness reports degraded because the optional components are absent. Check the response body: it names which component. A degraded readiness with the portable retrieval path in use is the normal local state.
Uploads accepted but nothing appears The worker is not running. Ingestion is queued in PostgreSQL, so the upload succeeds and the job simply waits. Start pnpm dev:worker; the queued jobs will drain. Support tools (Figure 15) shows the queue depth.
A job stays queued and never runs Check WORKER_MAX_ATTEMPTS and the job's state. Jobs that exhausted their attempts show as gave up rather than being retried forever. The failure reason is recorded without any memory content in it.
Everything a user does is refused Read the reason code in the Activity log. It names the specific gate — membership status, consent activity, sensitivity ceiling, restricted topic, embargo, missing recipient grant — rather than a generic denial.
An answer abstains when you expected content Three likely causes, in order: the memory is not approved yet (check Review stories); the topic is restricted in Permissions; or the source is excluded there. The system deliberately does not hint at which, so check the storyteller's settings directly.
The database returns zero rows for everything You are querying outside an archive scope. This is row-level security behaving correctly, not a data loss. Application code reaches data only through withArchiveAccess, which opens the scope; a manual psql session does not.
Migration refuses to apply A migration file changed after it was applied and its checksum no longer matches. Do not edit an applied migration — add a new numbered one.
Startup fails with a configuration error Working as intended. Configuration is validated by Zod at boot, so a missing or malformed value stops the process with a readable message instead of failing inside a request hours later. The message names the variable.
AUTH_DRIVER=local refused in production Also working as intended, and it means there is currently no production authentication path. See item 4 on the blocking list.
Playwright cannot find a browser Set PLAYWRIGHT_CHROMIUM_PATH to the Chromium binary. The config reads it rather than assuming a downloaded revision, because the bundled revision and the installed one disagreed in the build environment.
Never put memory content in an operational surface

Notification previews, email subject lines, analytics events, error logs and support dashboards must never carry memory content. This is enforced in the code that constructs each of them, and it is the rule most easily broken by a well-meaning debugging change. If you add a log line while chasing a bug, delete it before committing.
