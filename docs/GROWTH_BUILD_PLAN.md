## What v0.3 adds, and why in this order

The brief's own thesis: build the compounding loop first, then the moat, then
expansion behind evidence. The ordering below follows that and nothing else.

| Phase | Slice | Why it is where it is |
| --- | --- | --- |
| 1 | Family Question Inbox | The only slice that turns one storyteller into a loop. Everything after it compounds on more approved content; without it the archive is a one-person diary |
| 2 | Contributor loop | Second source of approved content, and the first place a malicious or careless relative can do damage — so it needs the review path the inbox establishes |
| 3 | Capsules + gift/reservation | The first commercial signal, and the first sharing surface that can leak |
| 4 | Gap radar, missions, multilingual | Retention and reach. Cheap once the loop exists; pointless before it |
| 5 | Portability and artefacts | The moat. Export, integrity manifest, book, QR |
| 6 | Knowledge graph and stewardship | Structure over content that already exists |
| 7 | Evidence-gated expansion | Flags and prototypes only. No P2 product without three paid design partners |
| 8 | Hardening and handoff | |

## The rule this plan is built to respect

The existing pipeline is:

```
authenticate → authorise → retrieve authorised P1–P3 evidence → detect
restrictions and contradictions → draft atomic third-person claims → verify
each claim → cite → answer or abstain → log content-free metadata
```

Every v0.3 slice enters that pipeline rather than going around it. A family
question's answer becomes a real `source_asset`, a real `transcript`, real
`transcript_segment` rows and a real `memory_candidate` — structurally
identical to an uploaded recording — so retrieval, citation opening, export and
deletion work on it with no special cases. A contributor's proposal is a
candidate, never an approved fact. That is the whole design.

## Definition of done, per slice

Unchanged from the brief, and enforced by review before a slice is called
complete: real UI on real backend behaviour, typed and validated, server-side
authorisation, migrations, tested archive isolation, consent and provenance
recorded, audit history, revocation and deletion defined and tested, loading /
empty / error / permission-denied states, accessibility tested, synthetic demo
data through the same domain paths, tests passing, limitations documented.
